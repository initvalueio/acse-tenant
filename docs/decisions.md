# Open decisions in the acse-tenant module

These are the judgement calls that spec 02e, its Amendments 1 to 4 and 6, ledger 02e (§0b, §10, §11, §12.8) and spec 02d A-4
leave to this module. For each one the table gives the default taken and what it would cost to change it.

**●** marks a call that is costly to reverse. Those calls are for the Architecture Owner, and the defaults stand only until he decides.

## the Architecture Owner's answers, verbatim (2026-11-07)

### DEC-6 (settings size)

> "Option 1 with the below changes
>
> Change 1: readers always go through the index, including for small sections. As worded, Option 1 says small sections stay a single parameter and readers always read the index first. Those two can’t both hold. Make settings/<section> always the index. When the payload fits, put it inline in the index; otherwise the index points to settings/<section>/0..n. That keeps one path shape for every section. It also means the promoter’s sections (outbox and naming, both small and bounded) stay inline, so its single GetParameters call from LT-1 still covers everything.
>
> Change 2: the index carries a digest, and the writer publishes the index last. SSM can’t write several parameters atomically. If the setup apply is halfway through overwriting /0 and /1 when the runtime reads, the runtime can get a mix of old and new parts. Put {commit, sha256, parts} in the index, write the parts before the index, and have readers check the digest after reassembling and retry if it doesn’t match. This fits what the system already does: the runtime records the merge sha and the file digest for tenant.yaml (OD-4/OD-5).
>
> Check who actually reads these two lists from the store. It may matter less than it looks. The runtime currently reads tenant.yaml straight from git through ACSE Read (tenant_config/load.py) and relays it from there. The promoter’s narrow role reads only settings/outbox and settings/naming. The gate workflow needs nothing from the store in per_repo mode, and in ruleset mode the gate list is exactly one entry. So the two large sections may have no store reader today. That doesn’t change the recommendation: the path shape still gets pinned, and splitting is cheap. But it means the splitting code isn’t on anyone’s critical path yet.
>
> Two smaller things:
>
> 8 KB is SSM’s Advanced tier; Standard is 4 KB. Confirm LM-1 actually provisions Advanced, or the real limit is 4 KB. Advanced costs $0.05 per parameter per month, so even a 25-part tenant costs almost nothing.
> LM-1 doesn’t exist yet. initvalueio/acse-tenant returns 404, so nothing is pinned so far. This is the cheapest point to make the decision."

### DEC-20 (setup credential)

> "Lets go with Option: customer-named secret but also look in to the below
> The recommendation is right, but choosing it has three consequences the card doesn’t mention.
>
> Why not inside the namespace. T-6 and §4 give the runtime GetSecretValue on all of acse/<tenant>/…. If an org-admin key sits under that prefix, ACSE’s runtime can read a credential that can rewrite the customer’s entire GitHub org. That undoes the least-privilege boundaries you’ve built: Change never holds workflows, GA-24 moved administration: read to Read only, and the promoter got a narrow role that reads only four entries. Excluding the path is possible, but then every customer’s IAM depends on a deny carve-out staying correct. One wildcard edit brings the key back into scope, and a regulated customer’s security review will flag it. The question to ask is whether ACSE can ever reach this key, and Option 1 is the only answer that’s no by construction.
>
> Consequence 1: Option 1 breaks T-4 as written, so amend it. T-4 says secrets live only under acse/<tenant>/…. State the reason for the exception in the spec: T-4 covers the credentials ACSE’s components use. The setup credential belongs to the customer’s bootstrap tier, like their own Terraform admin role, and is deliberately kept out of the namespace so that no ACSE identity can read it. Otherwise someone will “fix” the inconsistency later by moving it into the namespace.
>
> Consequence 2: who can assume the apply’s role matters more than where the key lives. The role that reads this secret should trust only acse-setup-apply.yml on the setup repo’s default branch. Ideally it should also require a GitHub environment with required reviewers. It must not be available to the PR job. The ledger has acse-setup-apply.yml running a PR-time check (LT-1/LM-1). If that job can assume the role, anyone who can open a PR in the setup repo can change the workflow on their branch and exfiltrate an org-admin key. Make the PR job a separate role with no access to the secret. It also needs to be distinct from cloud.workflow_role (the promoter’s) and from the runtime role.
>
> Consequence 3: “ephemeral” has a version floor. Reading the key through an ephemeral aws_secretsmanager_secret_version and passing it into the github provider’s app_auth needs Terraform 1.10 or later, which added ephemeral values in provider configuration. On OpenTofu, check that its ephemeral support covers provider blocks before relying on it. Pin the minimum version in the module. Below that floor the key ends up in the plan file, which is exactly what this option is meant to prevent.
>
> Two smaller points:
>
> Where the name lives. The secret’s name isn’t sensitive, so it can go in tenant.yaml or the module input. But ACSE can’t verify the secret exists because it can never read it. The Access stepper should show this step as “apply succeeded”, not as an ACSE probe.
> Cross-cloud. The same pattern works on GCP (Secret Manager plus Workload Identity Federation) and Azure (Key Vault plus federated credentials). Write the amendment to be cloud-neutral, since §3 already is."
